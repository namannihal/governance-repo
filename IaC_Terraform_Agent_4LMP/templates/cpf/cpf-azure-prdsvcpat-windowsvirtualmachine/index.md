# Windows VM Service Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for Windows VM deployment with multiple data disks. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

* **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
* **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific  infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
* **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
* **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
* **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
* **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Identity management
* Pattern provides the capability to deploy user managed identity for windows virtual machine which will be used for authentication between the Azure services.

### Secret management
 Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to enabled encryption on windows VM (Os & Data disk). AKV is utilized for two primary purposes.

* Storing the CMK Key.
* Managing the secrets for the Azure windows VM

### Networking
*  Azure Windows VM requires a Subnet as a prerequisite. Subnet creation is provided as an optional component. The deployment of a new subnet for the Windows VM depends on the property `use_existing_subnet`, if this property is set to `true`, the pattern will skip the subnet deployment along with `Network Security Group` and `Route Table` and it would be required to provide an existing subnet reference with `subnet_id`. However, if the `use_existing_subnet`, property is set to `false`, the pattern will deploy a new subnet along with `Network Security Group` and `Route Table`.

### Availability
* Deploy Windows VM across 2 availability zones in the Primary region for production/UAT environment.
* Windows VM Deployment in multiple availability zones can have an uptime SLA of 99.99%.

### Entra Id Support
* Entra ID–enabled Windows VMs were experiencing an issue where machines lost their domain association after a golden image refresh. This typically happens because identity bindings and registration states are not preserved correctly in generalized images.  This can be restified by <br>

   - Set enable_entra_auth == false and remove_aad_login == true while image refresh.
   - Check the status using run command from azure portal using dsregcmd /status after the successful completion of the pipline run(image refresh). The Vm should be de-registered from Entra IDnow.
   - Set enable_entra_auth == true and remove_aad_login == false and rerun the pipeline to add the VM back to Entra ID

### Other
* Using the service pattern it is possible create a Windows VM and attach multiple data disks.
* While using dedicated host, Virtual Machine size and host SKU should belong to the same family.
* Ensure that the Virtual Machine and associated resources are not part of a Proximity Placement Group if they are intended to be deployed to a dedicated host.

## Additional Information
1. Azure Entra Authentication is not tested in this pattern version.
2. As per the security controls the Backup Vault must enforce the restriction of immutable vault via Properties, `immutable vault settings` to ensure backup data is protected from malicious actors that could lead to loss of recovery points or deleted backups. Also, Backup Vault must enforce the lock immutability for the vault via Properties, `immutable vault settings`. In addition, Backup Vaults must enforce the use of Soft Delete if backups are being used with a retention period of a minimum of 30 days within Properties, soft delete settings in order to recover data after an accidental or malicious deletion and Backup Vaults must enforce the use of Always-On Soft Delete if backups are being used within Properties, soft delete in order to recover data after an accidental or malicious deletion and ensure data cant be deleted permanently.  
**Note: Due to above security control, once the backup is enabled for the Windows VM backup disk, and in case the disk is deleted, user will not be able to delete the backup vault as the Backup Item(s) cannot be deleted since it has active recovery points and the selected Vault is an immutable vault.**
3. The local value **rotation_policy** is immutable for the end user, which is for the disk encryption set. Keep the value same for future use.

### Build and Test
1. To deploy this pattern, add the module call in your repository and configure tfvars.
```tf
#--------------------------------------------------
# - Deploy Windows VM Pattern
#--------------------------------------------------
module "azure_prdsvcpat_terraform_windowsvirtualmachine" {
  source      = "../../"
  for_each    = var.windows_vm
  org_id      = var.org_id
  app_id      = var.app_id
  location    = var.location
  environment = var.environment
  context     = each.value.context
  instance    = each.value.instance
  tags        = var.tags
  #### Platform and Application Dependencies ####

  # resource_group_name         = "${split("/",var.resource_group_id)[4]}"
  resource_group_id           = var.resource_group_id
  shared_nrtbl_vnet_id        = var.shared_nrtbl_vnet_id
  privateendpoint_subnet_id   = var.privateendpoint_subnet_id
  firewall_private_ip_address = var.firewall_private_ip_address

  #### Pattern specific variables - Additional Resources Switches ####
  key_vault_config                  = each.value.key_vault_config
  network_config                    = each.value.network_config
  disk_encryption_set               = each.value.disk_encryption_set
  secure_boot_enabled               = each.value.secure_boot_enabled
  deploy_proximityplacementgroup    = each.value.deploy_proximityplacementgroup
  size                              = each.value.size
  admin_username                    = each.value.admin_username
  computer_name                     = each.value.computer_name
  source_image_id                   = each.value.source_image_id
  os_disk                           = each.value.os_disk
  identity_type                     = each.value.identity_type
  identity                          = each.value.identity
  des_identity_type                 = each.value.des_identity_type
  des_identity                      = each.value.des_identity
  additional_disk                   = each.value.additional_disk
  custom_data                       = each.value.custom_data
  key_vault_tags                    = var.key_vault_tags
  azure_backup                      = each.value.azure_backup
  password_expiration_date          = each.value.password_expiration_date
  capacity_reservation_groups       = each.value.capacity_reservation_groups
  availability_set                  = each.value.availability_set
  vm_agent_platform_updates_enabled = each.value.vm_agent_platform_updates_enabled
  enable_entra_auth = each.value.enable_entra_auth
  remove_aad_login  = each.value.remove_aad_login
}
```

1. Update the source with reference to the git repo with the version.
2. Check the terraform.tfvars file and update the values of org\\_id, app\\_id, location, context and instance for all the resources being deployed.
3. Update the values of variables in '.tfvars file'. In above example all `var.` varaibles are coming from the terraform.tfvars file in the .tests/deployTest folder.
4. **Note: Refer.tests/deployTest folder for sample code.**
