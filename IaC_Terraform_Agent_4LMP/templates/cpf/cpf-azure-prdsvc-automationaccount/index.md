# Automation Account module


## Overview

This terraform module creates a Automation Account, Runbook, Webhook and variables with the associated resources.

## Prerequisites

- An existing `Resource Group` and `User Assigned Identity`.
- For an Azure VM running as a Hybrid Runbook Worker, the VM Managed Identity should be utilized. Either the VM's User-assigned Managed Identity or the VM's System-assigned Managed Identity can be configured. This approach is not compatible with an Automation Account that has been configured with an Automation Account Managed Identity. Refer the link for more details(<https://learn.microsoft.com/en-us/azure/automation/automation-hrw-run-runbooks?tabs=ua-mi#runbook-auth-managed-identities>)

## Guidance

#### Usage

- This module allows to create Automation account along with `multiple` variables of kind `String`, `Integer`, `Boolean`, `Object`, `DateTime`
- Every kind of variable inside the automation account is `Optional` and `Encrypted`.
- The Azure API requires a publish_content_link to be supplied even when specifying your own content.
- One of `content, draft, publish_content_link` must be specified.

#### Security Considerations

- `azurerm_automation_credential` resource creation is not supported because of Policy [Custom-Automation Account-Credentials must not be stored-1.0.0](https://portal.azure.com/#view/Microsoft_Azure_Policy/PolicyDetail.ReactView/id/%2Fproviders%2FMicrosoft.Management%2FmanagementGroups%2Fa1a-dev%2Fproviders%2FMicrosoft.Authorization%2FpolicyDefinitions%2FCustom-AutomationAccounts-CredentialsMustNotBeStored-1.0.0/scopes~/%5B%22%2Fproviders%2FMicrosoft.Management%2FmanagementGroups%2Fa1a-dev%22%5D)
- However, `azurerm_automation_credential` resource block is added in module which allows user to create credentials if required, considering above `policy exemption` is there in place.
- Moreover, if you are trying to create automation variables (`int_var`, `bool_var`, `string_var`, `object_var`, `credential_var`) with **sensitive values** (e.g., from Key Vault secrets, marked as `sensitive = true`), then make sure to pass the `keys` in the corresponding iterator variable (`int_var_iterator`, `bool_var_iterator`, `string_var_iterator`, `object_var_iterator`, `credential_var_iterator`) as a `set of strings`. This is done to avoid exposing sensitive values directly in the for_each loop. For non-sensitive values, the iterator is optional and keys are automatically extracted. Refer examples as commented lines in `tests\deployTest` file for reference.
- Currently, `azurerm_automation_credential` accepts `null` value as default and even under `azurerm_automation_hybrid_runbook_worker_group` block, `credential_name` argument is optional.
- Further, Automation account `azurerm_automation_credential` block does not support `credential` creation via `Key Vault secrets` and `azurerm_automation_hybrid_runbook_worker_group` does not accept `Key Vault secrets` as credential.
