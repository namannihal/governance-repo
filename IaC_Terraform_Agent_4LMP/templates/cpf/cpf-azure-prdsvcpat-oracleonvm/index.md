# Oracle on VM Service Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for Oracle on VM deployment. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

* **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
* **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific  infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
* **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
* **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
* **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
* **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Identity management

* Pattern provides the capability to deploy user managed identity for Oracle database server, OEM Server & FSFO Server which will be used for authentication between the Azure services.

### Secret management
 Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to enabled encryption on the Oracle Database Server, OEM Server & FSFO Server. AKV is utilized for two primary purposes.
  * Storing the CMK Key.
  * Managing the public and private keys for the Oracle Database Server.

### Networking
* Oracle database on Azure VM requires a Subnet as a prerequisite. Subnet creation is provided as an optional component. Which would be deployed in LSEG complaint non routable VNET (scaffolded in application landing zone). The deployment of a new subnet for the Oracle Database depends on the property `use_existing_subnet`, if this property is set to `true`, the pattern will skip the subnet deployment along with `Network Security Group` and `Route Table` and it would be required to provide an existing subnet reference with `subnet_id`. However, if the `use_existing_subnet`, property is set to `false`, the pattern will deploy a new subnet along with `Network Security Group` and `Route Table`.

### Availability
* Oracle DB Servers will be deployed across 2 availability zones in the Primary region for production/UAT environment.
* Oracle Data guard will be used for database replication within availability zones and across region. Configuration of the replication is outside scope of this pattern.
* Oracle DB Deployment on multiple availability zones with the Oracle Data guard, can have an uptime SLA of 99.9%.

### Other
* Using the service pattern it is possible create desired number of Oracle databases servers.

## Additional Information
1. The initial version 0.1.0 is no longer supported. Please upgrade to the latest version 0.2.1. Below are the key changes to note when updating from 0.1.0 to 0.2.1:

`Group Names and IDs`: Updated patterns.
`User Creation`: Now creates two users: oracle and grid.
`Data Disk Provisioning`: Supports provisioning data disks larger than 2TB.
`Compatibility`: Ensures compatibility of data disk groups and databases with version 19.0.0.0.0.
`ASM Data Disks`: Added new ASM data disks: REDO1 and REDO2.
`nr_hugepages`: Updated to persist across VM restarts.
`Dynamic Disk Creation`: Added a new variable to dynamically create disks based on the specified number for ASM, Backup, REDO1, REDO2, and RECO disks.
`LUN Numbering`: Added a new loop to adjust LUN numbers according to the creation of ASM data disks, backup disks, swap disks, and RECO disks.
`Backup Considerations`: Updated backup filesystem type to LVM and included udev rules.
2. In some cases, where VM was created successfully but the script has failed, the recommended way to recover from this error is to remove the extension and rerun the template again.
3. The pattern by default creates 5 data disks which is required for Oracle installattion, the required disks are u01 disk, backup disk, swap disk, reco disk & asm disk. Pass the mandatory variables to create these disks from `tfvar` file, as shown in the `.tests\deployTest` folder.
4. Pattern does not support the capability to deploy additional data disk, for Oracle Virtual Machine. In case, there is a requirement to deploy additional disk, the same can be deployed by using the Cloud Product module. The usage example has been provided in the .tests/deployTest.
5. The bash script that installs Oracle requires the `bams_key` to authenticate to BAMS repository and this key is being passed through the CI/CD variables. The script also requires the `app_name` to be provided as part of the tfvar file, which will be used to generate the Database username.
6. The pattern provides a capability to enable Azure disk backup for Oracle VM backup disk which is an optional variable and can be enabled using `enable_backup`. When set to `true`, As per COE recommendation we take backup of only existing backup disks. This ensures that only relevant and available backup disks are captured. A Data Protection Backup Vault, Data Protection Backup Policy and a Data Protection Backup Instance for the Oracle VM Backup disk will be created. As per the security controls the Backup Vault must enforce the restriction of immutable vault via Properties, `immutable vault settings` to ensure backup data is protected from malicious actors that could lead to loss of recovery points or deleted backups. Also, Backup Vault must enforce the lock immutability for the vault via Properties, `immutable vault settings`. In addition, Backup Vaults must enforce the use of Soft Delete if backups are being used with a retention period of a minimum of 30 days within Properties, soft delete settings in order to recover data after an accidental or malicious deletion and Backup Vaults must enforce the use of Always-On Soft Delete if backups are being used within Properties, soft delete in order to recover data after an accidental or malicious deletion and ensure data cant be deleted permanently. **Note: Due to these security enforcement, once the backup is enabled for the Oracle VM backup disk, and in case the disk is deleted, user will not be able to delete the backup vault as the Backup Item(s) cannot be deleted since it has active recovery points and the selected Vault is an immutable vault.**

## Oracle Configuration
1. The logic behind the dynamic creation and assignment of disks in the infrastructure. The assignment of Logical Unit Numbers (LUNs) to disks ensures proper mounting and consistency. Disk Categories and Mount Points. The disks are created dynamically based on various configurations. The assignment follows the pattern:
    - u01 → 1 Disk → /dev/sdc
    - swap → Variable number of disks → /dev/sdd onward
    - backup → Disks allocated after swap → /dev/sdX
    - ASM Data Disks → Allocated after backup → /dev/sdX
    - Redo Logs → Allocated after ASM → /dev/sdX
    - Reco Disks → Allocated at the end → /dev/sdX
The assignment order ensures that all disks are created dynamically while maintaining a predictable mapping.
2. Required files & Log Files locations:
    - Response files are stored at /u01/mediafiles/responsefiles
    - Script logs are stored at - /var/log/Oracle_pattern-installation.log
    - Oracle ASM audit trail logs are written to /var/log/oraasmaudit.log file.
    - Oracle ASM disk logs are stored at /u01/mediafiles/ASM/configure_asm_disk_<current_date>.log
3. Based on the current configuration pattern supports the VM deployment with an SKU which supports temporary disk. The VM sku type for the Oracle VM must support temporary disk. Microsoft and Oracle recommends to use Azure’s temporary disk for an Oracle database. Please refer the link [Oracle Capacity Planning](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/scenarios/oracle-iaas/oracle-capacity-planning)
4. Following RHUI URLs should be whitelisted in Firewall:
    - rhui-1.microsoft.com
    - rhui-2.microsoft.com
    - rhui-3.microsoft.com
    - rhui4-1.microsoft.com
5. The script to install and configure Oracle, downloads binaries and Oracle set up from BAMS repositories, hence BAMS onboarding is must for the subscription the deployment is targetted to. For BAMS Onboarding refernce link (https://confluence.refinitiv.com/spaces/BAMS/pages/406865712/Onboarding)
6. After successful pipeline run with extensions, you need to restart vm from azure portal to view transparent hugepage disable configurations.
7. The variables oracle_version, oracle_golden_image_gridhome_url, and oracle_golden_image_dbhome_url have been added to parameterize Oracle version selection and golden image source URLs. By default, the build uses Oracle 19.15.0.0, but users can override these values in their .tfvars file to deploy a different version. For the latest Oracle Grid and DB golden image URLs corresponding to each supported version, please refer to the Confluence page: https://confluence.refinitiv.com/spaces/DCCE/pages/1541471226/Oracle+Grid+DB+versions+for+OVM+build…
