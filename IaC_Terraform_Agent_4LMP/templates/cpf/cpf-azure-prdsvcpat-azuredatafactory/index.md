# Azure Data Factory & Linked Service Service Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for Azure Data Factory deployment. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

- **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
- **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
- **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
- **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
- **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
- **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Secret management
Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to activate encryption on the SQL Managed instance. AKV is utilized for two primary purposes.

- Storing the CMK Key for data factory.
- Managing the secrets for the Azure windows VM

#### Additional Information
- Pattern provides the capability to deploy one Data Factory with one Self Hosted Integration Runtime with multiple nodes.
- Windows virtual machine service pattern is used to deploy the nodes for Self Hosted Integration Runtime. To create the virtual machine, pattern allows the capability for the user to decide the below:
  - Deploy a new subnet or use an existing subnet for the nodes (Virtual Machines). This is applicable for NSG and Route Table as well.
  - Pattern uses single Key Vault for storing CMK for Data Factory and Managing the secrets for Windows.
  - For more information on Windows Virtual Machine Service Pattern, please refer the [link](https://gitlab.dx1.lseg.com/app/app-51310/azure/prdsvcpat/terraform/azure-prdsvcpat-terraform-windowsvirtualmachine)
- Pattern supports the deployment of below linked services as aligned with base CPF modules:
  - Azure Key Vault
  - Azure SQL DB
  - Azure Function App
  - Azure SQL Managed Instance (SQLMI)
  - SFTP Server
  - Azure File Storage (with System/User Managed Identity, Account Key, or SAS Token authentication)
- Pattern supports fully parameterized deployment of Data Factory datasets:
  - Azure Blob Storage datasets with configurable linked service mapping
  - Custom REST API datasets with flexible linked service resolution
  - Supports automatic linked service name resolution from module outputs with graceful fallback to user-provided names
- Pattern supports fully parameterized deployment of Data Factory pipelines:
  - Configurable pipeline activities via JSON string input (`activities_json` variable)
  - Support for pipeline parameters, variables, annotations, and scheduling controls with concurrency configuration
  - Optional deployment via count meta-argument (set `datafactory_pipeline = null` to skip deployment)
- Pattern supports deployment of SSIS Integration Runtime with optional dedicated subnet creation and VNet integration for running SSIS packages
- Pattern can automatically create Azure File Shares for File Storage Linked Services using the Storage Share module
- Pattern creates System Managed Identity to connect to all Azure services that are using Azure AD integrated RBAC.
- Pattern also deploys User Managed Identity to enable CMK for data factory.

- To set-up SHIR nodes for Azure Data Factory, below URLs must be whitelisted in the firewall:
  - *.microsoft.com - Required by the self-hosted integration runtime for downloading the SHIR package into the target Virtual Machine and for downloading the updates.
  - adf.azure.com - SHIR needs to communicate with the Azure Data Factory service to perform data integration task and allowing adf.azure.com ensures that the SHIR can send and receive data and execute pipelines. Also allowing adf.azure.com ensures that the SHIR can securely connect to the service and perform its tasks without any interruptions.
  - *datafactory.azure.net - Required by the self-hosted integration runtime to connect to the Data Factory service. For newly created Data Factory, you can find the FQDN from Self-hosted ntegration Runtime key which is in format {datafactory}.{region}.datafactory.azure.net.
  - *.servicebus.windows.net - Required by the self-hosted integration runtime for interactive authoring.
  - Use this [link](https://lseg.service-now.com/esc?id=sc_cat_item&table=sc_cat_item&sys_id=0df298841b6a4290f369ea01b24bcbbd&searchTerm=firewall) to create a `Cloud SRE Request` to get the above URLs whitelisted.

## Pattern Usage

### Prerequisites

1. Route table and Non-route table Virtual networks
2. Peering between Route table and Non-route table Virtual networks

### Build and Test

1. Call the module whichever is needed to be deployed. As the example given below,

```tf
module "azure_prdsvcpat_terraform_azure_data_factory" {
  source      = "../../"
  org_id      = var.org_id
  app_id      = var.app_id
  location    = var.location
  environment = var.environment
  context     = var.context
  instance    = var.instance
  tags        = var.tags

  #### Platform and Application Dependencies ####
  resource_group_name       = var.resource_group_name
  resource_group_id         = var.resource_group_id
  shared_nrtbl_vnet_id      = var.shared_nrtbl_vnet_id
  azure_firewall_id         = var.azure_firewall_id
  privateendpoint_subnet_id = var.privateendpoint_subnet_id
   firewall_private_ip_address  = var.firewall_private_ip_address
  #### Azure Data Factory Service Pattern Variables
  key_vault_config = var.key_vault_config
  network_config   = var.network_config

  #### Azure Data Factory Service Pattern Variables
  resource_id          = var.resource_id
  private_endpoint_adf = var.private_endpoint_adf

  # VM variables
  win_vm_variables = var.win_vm_variables

  # Linked Services variables
  linked_service = var.linked_service

  # Dataset variables
  datafactory_dataset = var.datafactory_dataset

  # Pipeline variables
  datafactory_pipeline = var.datafactory_pipeline
}
```

1. Update the source with right tag version.
2. Check the terraform.tfvars file and update the values of org_id, app_id, location, context and instance for all the resources being deployed.
3. If the plan is use to use the existing resouce available on azure then please make an use of 'data block'
4. Update the values of variables in '.tfvars file'. In above example all `var.` varaibles are coming from the terraform.tfvars file in the .tests/deployTest folder.
5. **Note: The .tests/deployTest folder is for for deployment and unit test cases , Use only as reference and not as the exact implementation of the pattern.**
