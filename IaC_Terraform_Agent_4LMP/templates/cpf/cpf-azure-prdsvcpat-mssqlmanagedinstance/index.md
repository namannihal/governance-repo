# SQL Managed Instance Service Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for SQL Managed Instance deployment. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

- **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
- **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
- **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
- **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
- **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
- **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Secret management

Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to activate encryption on the SQL Managed instance. AKV is utilized for two primary purposes.

- Storing the CMK Key.
- Managing the local administrator password for SQL Managed Instance, constituting an exception process..

### Networking

- Azure SQL Managed instance requires a Subnet with delegation to SQL Managed Instance service. Subnet creation would be provided as an optional component which would be deployed in LSEG complaint non routable VNET (scaffolded in application landing zone). The deployment of a new delegated subnet for the SQL MI depends on the property `deploy_delegated_subnet`, if this property is set to `true`, the pattern will deploy a new delegated subnet along with `Network Security Group` and `Route Table`. If this property is set to `false`, the pattern will skip the delegated subnet deployment and it will expect the existing delegated subnet id as part of the property `delegated_subnet_id`.

-
  **Note: The same network settings is available for the networking in secondary region as well to deploy delegated subnet in secondary region**

### Availability

- The pattern supports for Geo redundant.
- The pattern supports for Zone redundant.

### Other

- Pattern provides the capability to deploy one SQL Managed Instance with desired number of SQL databases in the SQL managed instance server.

## Additional Information

1. `Security Alert Policies` - Storage accounts configured with `shared_access_key_enabled = false` cannot be used to configure `Security Alert Policy` with storage_endpoint. Hence the patterns enables `Security Alert Policy` without STorage Account.
   Also Storage is no longer required to hold Advanced Threat Protection Alerts. Use the storage picker to remove the storage configuration. Alerts can be viewed in Azure Security Center.
   Hence, the pattern allows to enable `Security Alert Policies` with Security Center & without Storage Account.
2. `Vulnerability Assessment` - `User Assigned Managed Identity` is supported when identity type is set to `SystemAssigned, UserAssigned`, since Vulnerability Assessment uses the System Assigned identity.
   The pattern uses RBAC-based access for `Vulnerability Assessment` with Storage Account.
   It grants `Storage Blob Data Contributor` to the System Assigned Identity at Storage Account scope.
   This avoids dependency on Storage Account Access Keys or Storage Container SAS keys.
3. The `Entra ID Authentication` for SQL MI has not been tested as it required additional permission - Managed Instance needs permissions to access Microsoft Entra ID.
   `Company Administrator` or a `Global Administrator` role is required to grant "Read" permissions to the principal that represents Managed Instance identity.
   Once the required access is granted, admin access can be granted using the variables `admin_object_id` & `admin_email`. To add multiple users, a group can be added as part of the `admin_object_id` & `admin_email`.
   Once enables, only AD users and Administrators can be used to login and the local database user login will be disabled.
   Both Entra ID and Password Authentication exists as per product design. Though Entra ID authentication only is highly recommended for SQL MI, password authentication is also supported.
4. The required [NSG rules](https://learn.microsoft.com/en-us/azure/azure-sql/managed-instance/connectivity-architecture-overview?view=azuresql&tabs=current#mandatory-security-rules-with-service-aided-subnet-configuration) & [Routes](https://learn.microsoft.com/en-us/azure/azure-sql/managed-instance/connectivity-architecture-overview?view=azuresql&tabs=current#mandatory-routes-with-service-aided-subnet-configuration) for SQL MI, has been added as part of this pattern.
   - The patterns deploys all the Required & Optional NSG rules for SQL MI.
   - Among the above NSG rules that SQL MI requires, there are rules that needs to be created in the Azure paired region for the chosen Primary region.
   - The pattern uses the variables `az_paired_region` & `az_paired_region_failover`to create the required NSG rules for the Azure Paired region for both Primary and failover delegated subnet. It is optional in case on secondary region delegated subnet NSG rule.
   - Refer the [link](https://teams.microsoft.com/l/message/19:00f38f32-b8ea-4904-a654-01bbcdd5615b_63a4cd3c-0d61-48dc-8312-159fd0910254@unq.gbl.spaces/1725346116081?context=%7B%22contextType%22%3A%22chat%22%7D) for the required and optional NSG and Routes.
5. Key vault key and secret supports only up to 15 tags. Please refer link:
- [Key vault key tags](https://learn.microsoft.com/en-us/azure/key-vault/keys/about-keys-details)
- [Key vault secret tags](https://learn.microsoft.com/en-us/azure/key-vault/secrets/about-secrets#secret-tags)
6. SQL Managed Instance deployment and deletion often takes around 3-5 hours for deployment, especially in cases where Zone Redundancy is enabled. So, please make sure to get Project Timeout and Vault secrets expiration timeout extended in pipeline to accommodate requirement of SQL Managed Instance product deployment.
7. For `storage_account_type` GEO-ZRS (`GZRS`) is currently not supported via Terraform with Azurerm 3.x for SQL Managed Instance. Confirmation from Hashicorp [Hashicorp case](https://github.com/hashicorp/terraform-provider-azurerm/issues/28449).
   - To enable `GZRS` use `storage_GZRS_enabled = true` which uses azapi to update the settings.
   - To enable `GZRS` in secondary region set mandatory variable `failover_storage_GZRS_enabled = true` which uses azapi to update the settings.

#### SQL Managed Instance Failover
1. SQL MI failover has been tested in paired region. To test the failover, peering between the Primary & Secondary VNETs is required. | The variable `failover_enabled` needs to set to `true`  to enable the failover.
2. As part of the failover, pattern provides the capability to deploy the below resources :
   - Keyvault with private endpoint
   - Storage Account & container
   - Private endpoint with record set for failover SQL MI for external connectivity
3. Azure SQL Managed Instances uses the same DNS zone for both the primary and secondary (failover) instances.
4. The pattern provides a capability to deploy the private endpoint for SQL managed Instance for both primary & secondary region, for external connectivity (from a different virtual network). Use boolean `deploy_sqlmi_pe` & `deploy_sqlmi_pe_failover`.
   The pattern supports using an existing private DNS zone. To use it, set `create_private_dns_zone = false` and provide `private_dns_zone_name`. If `create_private_dns_zone = true`, the pattern creates a new private DNS zone.
5. Role assignment of the failover cluster is now being managed by the CPF module. Users are encourage to use move block to nullify this change.   

   **Note** - This private endpoint is created only to establish connection from a different network. Connecting the same virtual network as a Virtual Network Link to the Private DNS zone will cause management operations to fail.
   Follow the below links for more details
   - [Private Endpoint for different virtual networks](https://learn.microsoft.com/en-us/azure/azure-sql/managed-instance/private-endpoint-overview?view=azuresql&tabs=separate-vnets)
   - [Private Link for Azure SQL MI](https://learn.microsoft.com/en-us/azure/azure-sql/managed-instance/private-endpoint-overview?view=azuresql&tabs=separate-vnets)
   - [Set up DNS for Private Endpoint for SQL MI](https://learn.microsoft.com/en-us/azure/azure-sql/managed-instance/private-endpoint-overview?view=azuresql&tabs=separate-vnets#set-up-domain-name-resolution-for-private-endpoint)
