# __Application Gateway Container app postgresql Pattern__ module

## Overview

This terraform module creates a __Application Gateway Containerapp Postgresql__ and associated resources.

Here are some of the key advantages the proposed solution offers:

- **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
- **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
- **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
- **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
- **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
- **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Identity management

* For connecting to Azure PostgreSQL, Microsoft Entra is the LSEG approved mechanism. Pattern supports the local authentication, but that requires an exception and the Azure policy exemption. In case, local autentication is required then Azure policy - `Custom-EntraIDAuthOnlyMustBeUsed-1.0.0` needs to be exempted before deployment.
* SPN used for deployment of pattern would get admin permission to the PostgreSQL Server automatically.
* Granting admin access to the additional user/SPN is provided as an optional component via the Microsoft Entra group.
* Container App enforce the use of Managed Identity to authenticate to Azure resources in order to adhere to the principle of least privilege and remove the need to store credentials using identity{} block in `azurerm_container_app` resource.

### Secret management

 Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to enabled encryption on the PostgreSQL server. AKV is utilized for two primary purposes.

* Managing the local administrator password for PostgreSQL, constituting an exception process for the policy.
* Azure Key Vault Private Endppoint pattern is offered as an optional component, and it serves as the repository for storing the Customer Managed Key (CMK) generated by the module CosmosDB Account. It is needed to activate encryption for Cosmos NoSQL data at rest. AKV is utilized for storing the CMK Key.
* In Container App, the access keys and connection strings generated by `Redis Cache` and `CosmosDB` respectively, which are further used for integration with containers in container apps are stored as a secret in the Key Vault through the Key Vault Private Endpoint Pattern in order to protect Secrets by using a secure storage mechanism.

### Networking

* The pattern provides flexibility to choose if the Azure PostgreSQL (Flexible) Server needs to be deployed with VNET integration or Private end point. By default the configuration for VNET inetgration is implemented.
* Azure PostgreSQL (Flexible) Server VNET integration requires a Subnet with delegation to PostgreSQL service. Subnet creation would be provided as an optional component. Which would be deployed in LSEG complaint non routable VNET (scaffolded in application landing zone). It also gets deployed with the required delegation to psql ("Microsoft.DBforPostgreSQL/flexibleServers") and service endpoint for Microsoft.Storage.
* Azure PostgreSQL (Flexible) Server requires a private DNS Zone for name resolution, Private DNS Zone creation is offered as an optional component. DNS Zone is linked to the both routable and Non-routable Virtual networks.

### Availability

* Service Pattern supports geo redundancy and zone replicas.

#### Cross-Region Architecture Considerations

This pattern supports two distinct cross-region strategies for disaster recovery:

##### 1. **Geo-Redundant Backup (Default - Passive Standby)**
   - **Use Case:** Cost-optimized DR with acceptable RTO/RPO
   - **Configuration:** Set `postgres_server.geo_redundant_backup_enabled = true`
   - **Behavior:** PostgreSQL read-only replicas in secondary region, BYOB (Application Gateway, Container Apps, etc.) remains in primary region
   - **Critical Requirement:** VNet peering must be enabled between primary and secondary regions for network connectivity
   - **Recovery Model:**
     - If primary region becomes unavailable, the BYOB infrastructure is also unavailable
     - Secondary region PostgreSQL replicas can be manually promoted to primary (manual failover required)
     - Best suited for scenarios where brief downtime is acceptable during regional outages

##### 2. **Active-Active Multi-Region Setup (Recommended for High Availability)**
   - **Use Case:** Zero-downtime DR with low RTO/RPO requirements
   - **Configuration:** Deploy entire pattern in multiple regions with independent BYOBs in each region
   - **Behavior:** Each region has its own Application Gateway, Container Apps, and PostgreSQL instances
   - **Prerequisites:**
     - VNet peering between all regions **must be enabled**
     - Load balancer or DNS-based routing across regional instances
     - Database replication configured between regional PostgreSQL instances
     - Application logic designed for multi-region consistency
   - **Recovery Model:**
     - Single region failure does not impact overall availability
     - Automatic failover via load balancer or DNS health checks
     - Both regions serve traffic simultaneously
     - Best suited for mission-critical workloads requiring near-zero downtime

#### VNet Peering Requirements for Cross-Region Deployments

When deploying this pattern across regions, **VNet peering must be established:**
   - Primary Region VNet ↔ Secondary Region VNet (bidirectional peering)
   - Enables BYOB infrastructure in primary region to access PostgreSQL resources in secondary region
   - Allows cross-region subnet communication for private endpoints and DNS resolution
   - Necessary for secondary region private DNS zones to be accessible from primary region

## Prerequisites

- Existing `resource_group` and `virtual_network`

### Cross-Region Prerequisites (if using Geo-Redundancy or Multi-Region Deployment)

**Important:** Before deploying this pattern with cross-region capabilities, ensure the following:

1. **VNet Peering:**
   - Establish VNet peering between the primary region VNet and any secondary/paired region VNets
   - Both directions must be enabled for proper bidirectional communication
   - This is **mandatory** for geo-redundant backup and active-active setups

2. **Network Connectivity:**
   - Verify network routes are configured to allow cross-region traffic
   - Ensure NSGs permit traffic from remote region subnets
   - Consider adding private endpoint routes for secondary region resources

3. **DNS Resolution:**
   - Link secondary region PostgreSQL private DNS zones to primary region VNets
   - This allows primary region applications to resolve secondary region database endpoints

4. **Regional Resource Planning:**
   - Determine disaster recovery strategy: Geo-Redundant Backup (passive standby) vs Active-Active
   - Plan for load balancing solution if using active-active approach
   - Consider data replication requirements between regions
