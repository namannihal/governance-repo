# Azure Functions Windows Service Pattern

[[_TOC_]]

This readme provides an overview of an service pattern for Azure Functions Windows. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

* **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
* **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific  infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
* **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
* **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
* **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
* **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Identity management

* Only via Microsoft Entra ID.

### Secret management

Azure Key Vault (AKV) is offered as an optional component.

* CMK for azure storage encryption
* Keys repository for different type of authorization scope like Admin, function, system key level

### Networking

* Connectivity is to be exposed only via Private Link Service (Private Endpoint)

### Availability

* Zone Redundandancy is configurable.

### Other

* NA
### Design Decisions

* Consumption Plan is not supported as it does not support VNET integration
* Support for both Entra authentication and keys level authentication
* No automatic backup support, as usage of Azure Storage redundancy options to ensure your storage account meets its availability and durability targets during an outage.

### Security Consideration

* Design will be based on Security MEC (https://lsegroup.sharepoint.com/:x:/s/SecurityArchitecture/EYQvir35WzRCmLxqDffLLdYBjpA_dLmEnrzPvmHPT8xjfA?e=YJC4MB )
* Admin management can be performed using via Azure Bastion to login in to Virtual machine through which this PaaS can be reached.

### HA & DR

* Support and guidance for Disaster Recovery across multiple region Active - passive for both https and non - http
* Support and guidance to support different ranges of RTO & RPO

### Back Up

* Azure functions content is in linked azure storage account, usage of Azure Storage redundancy options to ensure your storage account meets its availability and durability targets during an outage.

### Pattern Usage

#### Prerequisites

1. Routabe and Non-routable Virtual networks
2. Peering between Routabe and Non-routable Virtual networks

#### Build and Test

1. Call the module whichever is needs to be deployed. As the example given below,

    ```terraform
      module "azure-prdsvcpat-terraform-windowsfunctionapp" {
        source      = "git::https://gitlab.dx1.lseg.com/app/app-51310/azure/prdsvcpat/terraform/azure-prdsvcpat-terraform-windowsfunctionapp?ref=<pattern-version-tag>"

        app_id      = var.app_id
        location    = var.location
        environment = var.environment
        context     = local.context
        instance    = var.instance
        tags        = var.tags

        #### Platform and Application Dependencies ####
        resource_group_name         = var.resource_group_name
        shared_nrtbl_vnet_id        = var.shared_nrtbl_vnet_id
        firewall_private_ip_address = data.azurerm_firewall.afw[0].ip_configuration[0].private_ip_address
        privateendpoint_subnet_id   = var.privateendpoint_subnet_id

        #### Azure Functions - Linux Service Pattern Variables
        key_vault_config           = var.key_vault_config
        storage_account_config     = var.storage_account_config
        loganalytics_config        = var.loganalytics_config
        applicationinsights_config = var.applicationinsights_config
        appserviceplan_config      = var.appserviceplan_config
        network_config             = var.network_config

        #### Azure Functions - Linux Service Pattern Variables
        app_settings                          = var.app_settings
        builtin_logging_enabled               = var.builtin_logging_enabled
        client_certificate_enabled            = var.client_certificate_enabled
        client_certificate_mode               = var.client_certificate_mode

        enabled                               = var.enabled
        functions_extension_version           = var.functions_extension_version
        enable_systemassigned_identity        = var.enable_systemassigned_identity
        storage_accounts                      = var.storage_accounts
        backend_storage_key_vault_secret_id   = var.backend_storage_key_vault_secret_id
        backend_storage_uses_managed_identity = var.backend_storage_uses_managed_identity
    ```

2. Update the source with right tag version.
3. Check the terraform.tfvars file and update the values of org_id, app_id, location, context and instance.
4. If the plan is use to use the existing resouce available on azure then plase make an use of 'data block'
5. Update the values of variables in '.tfvars file'. In above example all `var.` varaibles are coming from the terraform.tfvars file in the .tests/deployTest folder.
6. **Note: The .tests/deployTest folder is for for deployment and unit test cases , Use only as reference and not as the exact implementation of the pattern.**
