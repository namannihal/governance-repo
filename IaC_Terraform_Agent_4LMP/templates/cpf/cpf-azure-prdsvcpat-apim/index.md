# API Management Service Pattern (Internal APIs)

[[_TOC_]]

This readme provides an overview of a service pattern for API Management(Internal APIs) deployment. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

- **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
- **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
- **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
- **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
- **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
- **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

## Pattern Description

This section contains the details of the azure service technical use case.

### Provisioned Azure services through IaC

- Azure Key Vault with Private Endpoint in Primary region.
- User managed identity for APIM.
- API Management Subnet.
- Network Security group and Route Table for Subnet(Optional).
- Public IP address (for management traffic - required by APIM)
- API Management and associated resources including Products, product policies, API's, APIM policy, API policies, subscriptions, certificates, custom_domains, operations,  operation_policies and product_apis.

### Identity management

- Pattern provides the capability to deploy user managed identity for API Management which will be used for authentication between the Azure services.

### Secret management

Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the application certificates.

### Networking

- Azure API Management requires a Subnet. Subnet creation would be provided as an optional component which would be deployed in LSEG complaint non routable VNET.
APIM can be deployed in an existing subnet by setting the parameter `use_existing_subnet` to `false` and `subnet_id`, please ensure that the subnet has delegation and required NSG rules. For use of deployment and avoid missing any dependency, we recommend to set `use_existing_subnet` to `true`, it will deploy a new  subnet along with `Network Security Group` and `Route Table`.
  **Note: For API gateway replication across secondary region ensure that the network settings are same in both the regions,refer this [link](https://learn.microsoft.com/en-us/azure/api-management/api-management-howto-deploy-multi-region) for additional details**

### Availability

- The pattern supports for Zone redundancy.

### Other

- Pattern provides the capability to deploy one API Management(Internal APIs) with desired number of API in the API Management.

## Route Table Migration (v1.0.0 Upgrade)

### Overview
The pattern has been upgraded to support Azure RM 4.x provider, which includes an upgrade of the route table module from v0.4.0 to v1.0.2. This upgrade changes how routes are managed - from dynamic blocks to separate resources.

### Migration Variable: `enable_route_migration_mode`

A new boolean variable `enable_route_migration_mode` (default: `false`) has been introduced to handle different deployment scenarios:

| Scenario | Variable Setting | Behavior | Use Case |
|----------|------------------|----------|----------|
| **New Deployments** | `false` (default) | Creates default APIM routes automatically (`apimroute`, `0-route-01`, `10-route-02`, `172-route-03`) | Fresh infrastructure deployments |
| **Existing Deployments** | `true` | Skips default route creation to avoid conflicts with existing routes | Migration from older pattern versions |

### Default Routes Created

When `enable_route_migration_mode = false`, the following routes are automatically created:

- **apimroute**: `ApiManagement` → `Internet` (for API Management service endpoints)
- **0-route-01**: `0.0.0.0/0` → `Azure Firewall` (default route via firewall)
- **10-route-02**: `10.0.0.0/8` → `Azure Firewall` (private network range via firewall)
- **172-route-03**: `172.16.0.0/12` → `Azure Firewall` (private network range via firewall)

### Migration Workflow

#### For Existing Deployments (Upgrading from older versions):
1. Set `enable_route_migration_mode = true` in your terraform configuration
2. Run `terraform plan` to verify no route conflicts
3. Run `terraform apply` to upgrade the pattern
4. Existing routes remain unchanged and functional

#### For New Deployments:
1. Use default `enable_route_migration_mode = false` (or omit the variable)
2. Deploy as normal - all default routes will be created automatically
3. Full APIM functionality available immediately

### Example Configuration

```hcl
# For existing deployments (migration)
module "azure-prdapppat-terraform-apim" {
  source = "path/to/pattern"
  # Migration setting for existing deployments
  enable_route_migration_mode = true
  # Other configuration...
  org_id      = var.org_id
  app_id      = var.app_id
  # ...
}

# For new deployments
module "azure-prdapppat-terraform-apim" {
  source = "path/to/pattern"
  # Default setting (false) - creates all default routes
  # enable_route_migration_mode = false  # Optional - this is the default
  # Other configuration...
  org_id      = var.org_id
  app_id      = var.app_id
  # ...
}
```
