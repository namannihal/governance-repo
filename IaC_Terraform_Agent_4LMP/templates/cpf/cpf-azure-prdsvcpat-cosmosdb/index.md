# CosmosDB Service Pattern

[[_TOC_]]

This readme provides an overview of an service pattern for CosmosDB. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

* **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
* **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific  infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
* **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
* **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
* **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
* **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Provisioned Azure services through IaC

* Azure Keyvault Service (AKV) with Private Endpoint (Optional)
* Azure CosmosDB account
* Azure Cosmos DB for MongoDB Database (Optional - As configured in the CosmosDB account)
* Azure Cosmos DB for NoSQL Database (Optional - As configured in the CosmosDB account)
* Azure Cosmos DB for NoSQL Container (Optional - As configured in the CosmosDB account)
* Azure Cosmos DB Cassandra Keyspace and Table (Optional - As configured in the CosmosDB account)
* User Managed Identities
* Azure Private Endpoints.

### Identity management

* Pattern provides CosmosDB mongo role definition.
* Pattern provides CosmosDB mongo user definition.
* Local account users to be supported - Exception needs to be taken for the deployment of Azure Cosmos DB for MongoDB.
* Azure CosmosDB may follow RBAC based on the following roles and RBAC would be managed outside the pattern. Refer to the [link](https://learn.microsoft.com/en-us/azure/cosmos-db/role-based-access-control) for more info.

### Secret management

 Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to activate encryption on the Azure Cosmos DB for Mongo DB. AKV is utilized for below primary purposes.

* Storing the CMK Key.
* Storing the Connection Strings and access Keys for the Databases.
* Storing the Initially Random Password and Username - for Azure Cosmos DB for MongoDB. This needs to be Changed post deployment as per LSEG standard. This is out of scope of the pattern.

### Networking

* Pattern services are to be deployed in LSEG complaint non routeable VNET (scaffolded in application landing zone) only
* Connectivity is to be exposed only via Private Link Service (Private Endpoint)

### Availability

* Support for Availability Zones
* Support for Geo-Replication with support for read replicas and multiple-location-write replica.

### Other

* Pattern to support creation of Azure CosmosDB account and multiple Azure Cosmos DB for Mongo DB databases
* Pattern to support creation of Azure CosmosDB account and multiple Azure Cosmos DB for NoSQL databases
* Pattern to support creation of Azure CosmosDB account and multiple Azure Cassandra Keyspaces and Cassandra Tables.
### Design Decisions

NA

### Security Consideration

* Public access to be disabled
* Data at rest to be encrypted by FIPS 140-2 validated cryptographic module for storage encryption (Customer Managed Key)
* User assigned Identities for Authentication
* Design will be based on Security MEC (<https://lsegroup.sharepoint.com/:x:/s/SecurityArchitecture/EYQvir35WzRCmLxqDffLLdYBjpA_dLmEnrzPvmHPT8xjfA?e=YJC4MB> )
* Admin management can be performed using via Azure Bastion to login in to Virtual machine through which Azure Cosmos DB for Mongo DB service can be reached.

### HA & DR

* Support and guidance for Disaster Recovery across multiple region
* Support and guidance for active geo replication and failover to support different ranges of RTO & RPO.

### Back Up

* Pattern to support both continuous and periodic backup.
* Backup to support configuration of geo redundancy
* Pattern to support Restore from backup.

## Pattern usage Guidance

### Pattern Use Cases

| Use Case                                          | Default Behavior                                                     | Input Control - variable            | Comments                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploy Azure KeyVault or use an existing Keyvault | By Default the patterns deploys Keyvault                             | `key_vault_config.deploy_kv_and_pe` | The variable `key_vault_config.deploy_kv_and_pe` if set to true deploys the Azure keyvault with private endpoint the configurations of this keyvault can be manged under the key_vault_config variable.to use existing keyvault use the `key_vault_config.key_vault_id` input and set `key_vault_config.deploy_kv_and_pe` to false. |
| Deploy Azure Cosmos DB for NoSQL                  | The variable `cosmos_api` accepts `"sql", "mongo" and "Cassandra"` as inputs.        | `cosmos_api`                        | The variable `cosmos_api` if set to `"sql"` deploy with the kind `GlobalDocumentDB` and if set to `"mongo"` deploy with the kind `MongoDB`                                                                                                                                                                                          |
| Enable System Assigned Identity                   | By Default the patterns deploys CosmosDB with user assigned identity | `enable_systemassigned_identity`    | The variable `enable_systemassigned_identity` if set to true deploys the Azure CosmosDB with System Assigned identity along with the user assigned identity.                                                                                                                                                                        |

### Additional Information

* When multiple geo-locations are needed, please ensure the arguments `max_interval_in_seconds` set to more than 5 minutes and `max_staleness_prefix` set to more than 100000.
* Cosmosdb account needs to be created. While deploying cosmosdb account for mongo database, please ensure local_authentication_disabled argument set to False.
* This module deploys the mongo database.
* Azure Cosmos DB for MongoDB offers two resource types with different architectures.
  * 'Request unit (RU) database accounts'
  * 'vCore clusters'
* vCore cluster aka Mongo cluster can only be provisioned over portal. This resource type is currently not available with terraform provider 'azurerm' in the current version.
Regular Mongo Database is created by default using the resource type azurerm_cosmosdb_mongo_database.
* It's observed that 'analyticalStorageTtl' property in Cosmosdb sql container has a one to one relationship with the attribute 'analytical_storage_enabled' which needs to be set as true in 'azurerm_cosmosdb_account' resource while provisioning the container.

### Pattern Usage

#### Prerequisites

1. Routeable and Non-routeable Virtual networks
2. Peering between Routeable and Non-Routeable Virtual networks

#### Build and Test

1. Call the module whichever is needs to be deployed. As the example given below,

    ```tf
      module "azure-prdsvcpat-terraform-cosmosdb" {
        source      = "../../"
        org_id      = var.org_id
        app_id      = var.app_id
        location    = var.location
        environment = var.environment
        context     = local.context
        instance    = var.instance
        tags        = var.tags

        #### Platform and Application Dependencies ####
        resource_group_name       = var.resource_group_name
        privateendpoint_subnet_id = var.privateendpoint_subnet_id

        #### Azure CosmosDB Service Pattern Variables
        key_vault_config = var.key_vault_config
        network_config   = var.network_config

        #### Azure CosmosDB Service Pattern Variables
        offer_type                     = var.offer_type
        schema_type                    = var.schema_type
        total_throughput_limit         = var.total_throughput_limit
        create_mode                    = var.create_mode
        cosmos_api                     = var.cosmos_api
        is_parse_kind                  = var.is_parse_kind
        consistency_policy             = var.consistency_policy
        geo_location                   = var.geo_location
        ip_range_filter                = var.ip_range_filter
        combined_policy                = var.combined_policy
        capabilities                   = var.capabilities
        virtual_network_rule           = var.virtual_network_rule
        backup                         = var.backup
        cors_rule                      = var.cors_rule
        enable_systemassigned_identity = var.enable_systemassigned_identity
        restore                        = var.restore
        customer_managed_key           = var.customer_managed_key

        cosmosdbsqldatabase    = var.cosmosdbsqldatabase
        cosmosdbmongodatabases = var.cosmosdbmongodatabases
        depends_on             = []
      }
    ```

2. Update the source with right tag version.
3. Check the terraform.tfvars file and update the values of org_id, app_id, location, context and instance.
4. If the plan is use to use the existing resource available on azure then please make an use of 'data block'
5. Update the values of variables in '.tfvars file'. In above example all `var.` variables are coming from the terraform.tfvars file in the .tests/deployTest folder.
6. **Note: The .tests/deployTest folder is for for deployment and unit test cases , Use only as reference and not as the exact implementation of the pattern.**
