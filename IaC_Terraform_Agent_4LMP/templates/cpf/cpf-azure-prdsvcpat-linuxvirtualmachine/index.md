# Linux VM Service Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for Linux VM deployment with multiple data disks. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

* **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
* **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific  infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
* **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
* **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
* **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
* **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

### Identity management
* Pattern provides the capability to deploy user managed identity for Linux virtual machine which will be used for authentication between the Azure services.

### Secret management
 Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to enabled encryption on Linux VM (Os & Data disk). AKV is utilized for two primary purposes.

* Storing the CMK Key.
* Managing the secrets for the Azure Linux VM

### Networking
*  Azure Linux VM requires a Subnet as a prerequisite. Subnet creation is provided as an optional component. The deployment of a new subnet for the Linux VM depends on the property `use_existing_subnet`, if this property is set to `true`, the pattern will skip the subnet deployment along with `Network Security Group` and `Route Table` and it would be required to provide an existing subnet reference with `subnet_id`. However, if the `use_existing_subnet`, property is set to `false`, the pattern will deploy a new subnet along with `Network Security Group` and `Route Table`.

### Availability
* Deploy Linux VM across 2 availability zones in the Primary region for production/UAT environment.
* Linux VM Deployment in multiple availability zones can have an uptime SLA of 99.99%.

### Other
* Using the service pattern it is possible create a Linux VM and attach multiple data disks.
* While using dedicated host, Virtual Machine size and host SKU should belong to the same family.
* Ensure that the Virtual Machine and associated resources are not part of a Proximity Placement Group if they are intended to be deployed to a dedicated host.

## Additional Information
1. Azure Entra Authentication is tested in this pattern version.
2. As per the security controls the Backup Vault must enforce the restriction of immutable vault via Properties, `immutable vault settings` to ensure backup data is protected from malicious actors that could lead to loss of recovery points or deleted backups. Also, Backup Vault must enforce the lock immutability for the vault via Properties, `immutable vault settings`. In addition, Backup Vaults must enforce the use of Soft Delete if backups are being used with a retention period of a minimum of 30 days within Properties, soft delete settings in order to recover data after an accidental or malicious deletion and Backup Vaults must enforce the use of Always-On Soft Delete if backups are being used within Properties, soft delete in order to recover data after an accidental or malicious deletion and ensure data cant be deleted permanently.  Soft delete option is parameterised currently to accommodate testing but it should always set as **AlwaysOn**. <br>
**Note: Due to above security control, once the backup is enabled for the Linux VM backup disk, and in case the disk is deleted, user will not be able to delete the backup vault as the Backup Item(s) cannot be deleted since it has active recovery points and the selected Vault is an immutable vault. The soft delete setting controls the protection of backup instances. Available options are AlwaysOn, On, and Off. It is strongly recommended to use AlwaysOn, as disabling it may leave backups vulnerable to accidental deletion. Users are fully responsible for ensuring the safety and recoverability of their backup data.**
### Managed Disk IOPS and Throughput Configuration
The `managed_disk` variable supports custom IOPS and throughput settings via `disk_iops_read_write`, `disk_mbps_read_write`, `disk_iops_read_only`, and `disk_mbps_read_only`. When using these, be aware of the following constraints:

**1. Storage account type must be `PremiumV2_LRS` or `UltraSSD_LRS`.**
Custom IOPS and throughput values are only supported on Premium SSD v2 and Ultra Disk storage types. If you set these values on a `Standard_LRS`, `StandardSSD_LRS`, or `Premium_LRS` disk, Azure will reject the request with a `400 Bad Request` error.

**2. PremiumV2_LRS disks only support caching type `None`.**
Setting `caching` to `ReadWrite` or `ReadOnly` on a PremiumV2_LRS disk will fail with: *"Storage Account type PremiumV2_LRS is not supported with caching type ReadWrite. Please use caching type None."* Always set `caching = "None"` for PremiumV2_LRS and UltraSSD_LRS disks.

**3. PremiumV2_LRS disks are incompatible with Availability Sets and require zonal deployment.**
PremiumV2_LRS disks do not support fault domain alignment used by Availability Sets. Attaching a PremiumV2_LRS disk to a VM in an Availability Set will fail with: *"background copy of the data for fault domain alignment is not supported"*. To resolve this:
- Set the VM `zone` to a specific availability zone (e.g. `"1"`, `"2"`, or `"3"`).
- Set `deploy_availability_set` to `false`.
- Set the managed disk `availability_zone` to the **same zone** as the VM.
For more details, see the [Azure documentation on Availability Sets with Premium SSD v2](https://aka.ms/AvSetWithPv2).<br>
**4. DES with UserAssigned identity type is not supported for disk having PremiumV2_LRS' SKU in EAST US 2,as of 12-03-2026**
