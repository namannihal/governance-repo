# Orchestrated Virtual Machine Scale Set Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for `azure-prdsvcpat-terraform-orchestratedvmssdiskkeyvault`. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

- **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
- **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
- **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
- **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
- **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
- **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

## Overview

This terraform module creates an Orchestrated Virtual Machine Scaleset and associated resources.

## Pattern Description

This section contains the details of the azure service technical use case.

The following diagram shows the High Level Design for **Service pattern for Orchestrated VMSS Pattern**:

[Image: OrchestratedVMSSsvcpatHLD]

### Provisioned Azure services through IaC

- Key Vault Private Endpoint Pattern (Optional)
- Azure Disk Encryption Set
- Azure Loadbalancer
- Virtual Machine Scaleset in Flexible Orchestration Mode.
- Azure Monitor and Autoscale setting

#### Simplified Usability

- This pattern significantly reduces user time and effort by eliminating the need to individually call each of the above mentioned modules. Instead, users can focus on passing the `required parameters` after invoking this service pattern.
- Additionally, this pattern seamlessly integrates essential resource blocks, such as the `time_sleep` block, which introduces necessary delays to ensure sufficient time for DNS zone establishment when configuring private endpoints for core products such as Key Vault, which is created for CMK for Orchestrated VMSS, thereby ensuring the smooth creation of child resources.

### Secret Management

- Azure Key Vault Private Endpoint pattern is offered as an optional component, and it serves as the repository for storing the Customer Managed Key (CMK) generated by the module Disk Encryption set. It is needed to activate encryption on the disks attached to the instances of Orchestrated Virtual Machine Scale Sets. AKV is utilized for storing the CMK Key.
- Orchestrated VMSS allows the user to choose the dynamic OS. In Linux VM type, the SSH Key to be used by user to login to the Linux Virtual Machine which is passed through `admin_ssh_public_key`, is stored as a secret in the Key Vault through the Key Vault Private Endpoint Pattern in order to protect keys by using a secure storage mechanism. In Windows VM type, the admin password used by user to login to the Windows Virtual Machine is stored as a secret in the Key Vault through the Key Vault Private Endpoint Pattern in order to protect keys by using a secure storage mechanism.

### Identity Management

- Orchesrated Virtual Machines in flexible mode enforces the use of User Assigned Managed Identity to authenticate to Azure resources in order to adhere to the principle of least privilege and remove the need to store credentials using `identity{}` block in `azurerm_orchestrated_virtual_machine_scale_set` resource.

### Encryption

- CMK is enabled on the Orchestrated VMSS for both OS and data disk through disk encryption sets.
- Virtual Machine enables Encryption at host within the Disks in order to encrypt temporary disks, disk caches and data flow to storage service. This is enforced by setting `encryption_at_host_enabled = true`.
- The pattern provides an option for disk encryption set to be created for CMK to be enabled for the Orchestrated VMSS. If the user has an existing DES, the Orchestrated VMSS module can be invoked rather than the pattern and the ID of the DES created can be passed for it to be linked to the VMSS during creation.
- A 1:1 mapping of the respective VMSS to the disk encryption set is supported. Hence, if multiple VMSS are being created, they shall be individually mapped to a different Disk Encryption Set.

### Networking

- Orchestrated Virtual Machines enforce a network guardrail to prevent data exposure to the internet. This is enforced without using the optional parameter `public_ip_address_id` for each IP configuration defined in the Network Interface created.
- IP Forwarding is disabled on Network Interfaces to prevent unauthorised routing between network zones operating at different trust levels which is enforced by setting `enable_ip_forwarding = false` for the of Network Interface created.
- In Orchestrated VMSS Flexible Mode in Azure, each VM can have multiple network interfaces (NICs), allowing deployment across multiple subnets and more flexible network architectures. You can associate public IP addresses with individual NICs for external access. By default, IP forwarding is disabled (false), but it can be enabled for use cases like routing. Outbound connectivity is managed through Load Balancer NAT rules, allowing the VMSS to scale without interrupting outbound traffic. The Azure Load Balancer ensures traffic is distributed evenly across VM instances, improving availability and performance.

#### Autoscaling

- By default, Orchestrated VMSS will be created with manual scaling and maintaining a fixed instance count. If the user wishes to switch to custom autoscaling, they can do so by leveraging the `azure-prdsvc-terraform-monitorautoscalesetting` module.
- The maximum number of instances configured through autoscaling is also limited by the amount of cores available in the subscription.

### Golden Images

- Virtual Machines only use LSEG Security Architecture approved golden images or marketplace VM images to operate with security hardened and patched images that are preinstalled with LSEG mandated agents.
- If golden images are to be used, then the latest list of LSEG approved golden images are [here](https://lsegroup.sharepoint.com/sites/CloudCentral/SitePages/Golden-Pages--Page-Restructuring.aspx).
- The Azure Golden Image LSEG.com Dev subscription a1a-51386-dev-sub-gimage-01 is not compliant and therefore cannot be upgraded as a result, we will need to decommission the subscription by 1st October 2024. To continue consuming images from the LSEG.com Dev environment, a new subscription has been created: a1a-51386-dev-test-sub-gimage-02. This new subscription is compliant and contains up-to-date golden images which you can use right away.

#### Availability

- The pattern uses Zones for high availability and application resiliency. Also uses `zone_balance` to evenly distribute virtual machines in the scale set across the availability zones.

### Monitoring and Logging

- Azure Virtual Machine sends all diagnostic logs to a central SOC Log Analytics workspace through DINE (Azure) policy within its Diagnostic settings in order to support a security investigation after a security incident involving a linux Virtual Machine. This is not applicable for instances running in Virtual Machine Scale Sets.
- Azure Virtual Machine sends all diagnostic logs to a central SOC Storage Account through DINE (Azure) policy within its Diagnostic settings in order to provide a copy to adhere to compliance requirements. This is not applicable for instances running in Virtual Machine Scale Sets.

### Other

- Pattern provides the capability to deploy orchestrated virtual machine scale set with disk encrypted along with private endpoint.
- The variable `key_vault_id` takes the resource ID of a key vault as input for storing disk encryption keys and SSH Key for linux VM or windows admin password for windows VM , for login as secret.
  If a key vault with specified resource ID does not exist or you pass null in place of a valid resource ID, this pattern will create a new key vault and the name of new key vault will be as per the values of the LSEG naming variables.
  In this case the key vault is created in the same resource group specified as a target of the pattern deployment, not in the resource group specified by the non existing key vault resource ID.

## Additional Information

- By default, this pattern creates Orchestrated Virtual Machine Scale Sets with the Flexible Orchestration Mode and OS disks with storage account type as `Standard_LRS, StandardSSD_LRS, StandardSSD_ZRS, Premium_LRS and Premium_ZRS` to back the internal OS disk. The scaling mode is manual by default where we maintain a fixed number of instances.
- This pattern provides the flexibility to use AutoScale Set as optional feature. By setting this `var.vmss_autoscale.enabled` to true/false either enables or disables the feature.
- To protect your Virtual Machine Scale Sets from datacentre-level failures, you can create a scale set across Availability Zones. This can be done through three zonal deployment models :
    - Zone redundant or zone spanning
    - Zonal or zone aligned (single zone)
    - Regional
- Zone redundant or zone spanning -
    - A zone redundant or zone spanning scale set spreads instances across all selected zones, this is done by passing a list of availability zones to `zones` parameter, for example `zones = ["1","2","3"]`. By default, the scale set performs a best effort approach to evenly spread instances across selected zones.
    - A strict zone balance by setting `zoneBalance = true` can be specified. Each VM and its disks are zonal, so they are pinned to a specific zone. Note that this can be set only if the zones property of the scale set contains more than one zone.
    - A best practice would be to configure `autoscale` rules based on CPU or memory usage. The autoscale rules would allow the scale set to respond to a loss of the VM instances in that one zone by scaling out new instances in the remaining operational zones.
- Zonal or zone aligned (single zone) - A zonal or zone aligned scale set places instances in a single availability zone, for example `zones = ['1']`. Each VM and its disks are zonal, so they are pinned to a specific zone. This configuration is primarily used when you need lower latency between instances.
- Regional - A regional Virtual Machine Scale Set is when the zone assignment isn't explicitly set, for example `zones = [] or zones = null`. In this configuration, the scale set creates Regional (not-zone pinned) instances and implicitly places instances throughout the region.
- With Flexible orchestration, Azure provides a unified experience across the Azure VM ecosystem. Flexible orchestration offers high availability guarantees (up to 1000 VMs) by spreading VMs across fault domains in a region or within an Availability Zone
    - Max spreading by setting `platform_fault_domain_count = 1`
    - Static fixed spreading by setting `platform_fault_domain_count= 5`
    - Spreading aligned with storage disk fault domains by setting `platform_fault_domain_count = 2 or 3` for regional deployments only
- `platform_fault_domain_count` must be set to 1 or 5. Fixed spreading with 2 or 3 fault domains isn't supported for zonal deployments.
- Flexible orchestration mode provides the highest scale and configurability for VM sizes that support memory preserving updates or live migration such as when using the B, D, E and F-series or when the scale set is configured for maximum spreading between instances platformFaultDomainCount=1
- Virtual Machine Scale Sets in Flexible Orchestration mode manage standard Azure VMs. You have full control over the virtual machine lifecycle, as well as network interfaces and disks using the standard Azure APIs and commands.
- We can create `data_disk` in the Managed Disk module but cannot attach to the VMSS modules from Terraform hence, we have included the `data_disk` block to support multiple creation of data disks while deploying VMSS.
- A Standard Loadbalancer is deployed using the `azure-prdsvc-terraform-loadbalancer` module to configure outbound connectivity for the VMSS.
- It is not mandatory to create a profile, (however recommended) while creating VMSS in flexible orchestratation mode via AZ apis and cli commands.
- Flexible VMSS uses dynamic Azure Virtual machines which can be accessed and configured separately.
- Adding new VMs to the Orchestrated VMSS in flexible mode is possible regardless of different VM types (windows/ linux), sku and spot/non-spot configurations.
- When configuring application monitoring, one must install and configure the Application Health Extension if using Flexible Orchestration.
- The `Plan` block accepts specific Marketplace images from [Image Marketplace Portal](https://azuremarketplace.microsoft.com/en-us/marketplace/apps?filters=virtual-machine-images) which has the arguments referencing to categories of the images similar to `source_image_reference`, example:
  ```tf
    plan = {
      name      = "22_04-lts-gen2"
      product   = "0001-com-ubuntu-server-jammy"
      publisher = "Canonical"
   }
  ```
However, if you are using this block, it will need an acceptance of the legal terms of the Image on Subscription. To do it, please refer the [link](https://learn.microsoft.com/en-us/cli/azure/vm/image/terms?view=azure-cli-latest). Hence, we have kept as null for now and creating VMSS using `source_image_reference` block.
- Azure Site Recovery and Azure Backup are not supported in flexible mode, which can be a significant limitation for disaster recovery and backup strategies.
- Flexible mode lacks granular Role-Based Access Control (RBAC) permissions for individual VMs, limiting fine-grained access control.

## Pattern Usage

### Prerequisites

- A Resource Group where you want to create the Linux Virtual Machine Scale Set.
- A Virtual Network and Subnet where you plan to deploy the Private Endpoint for Key Vault, used for CMK for Linux VMSS.
- Network Connectivity : If you have multiple Virtual Networks, you need to setup the connectivity between the Virtual Network containing Gitlab Pipeline runner and the Virtual Network where you plan to deploy the Private Endpoints for the Key Vault.
- Only User Assigned Identity can be used.
- API Version: Use the appropriate API version (2021-03-01 or higher) for creating and managing VMSS in flexible mode.
