# Azure SQL Database Service Pattern

[[_TOC_]]

This readme provides an overview of an service pattern for Azure SQL Database. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

* **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
* **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific  infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
* **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
* **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
* **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
* **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

* Private Endpoint - Queue  (Optional).
* Private Endpoint - Table  (Optional).

* Private Endpoint - Fileshare  (Optional).

### Identity management

* Only via Microsoft Entra ID via Group object ID
* Granting admin access to the additional user/SPN is provided as an optional component via the Microsoft Entra group.

### Secret management

Azure Key Vault (AKV) is offered as an optional component, and it serves as the repository for the Customer Managed Key (CMK) needed to activate encryption on the SQL server. AKV is utilized for below primary purposes.

* Storing the CMK Key.

### Networking

* Pattern services are to be deployed in LSEG complaint non routable VNET (scaffolded in application landing zone) only
* Connectivity is to be exposed only via Private Link Service (Private Endpoint)

### Availability

* Support for Geo Redundant
* Support for Zone Redundant

### Other

* Supports creation of multiple Azure SQL databases

### Design Decisions

* No Local account users to be supported

### Security Consideration

* Public access to be disabled
* Data at rest to be encrypted by TDE managed via CMK (Customer Managed Key)
* User assigned Identities for Authentication
* Design will be based on [Security MEC](https://lsegroup.sharepoint.com/:x:/s/SecurityArchitecture/EYQvir35WzRCmLxqDffLLdYBjpA_dLmEnrzPvmHPT8xjfA?e=YJC4MB )
* Admin management can be performed using via Azure Bastion to login in to Virtual machine through which Azure SQL service can be reached.

### HA & DR

* Support and guidance for Disaster Recovery across multiple region.
* Support and guidance for active geo replication and failover groups to support different ranges of RTO & RPO

### Back Up

* Pattern to support both point in time and long term retention based on policies
* Backup to support configuration of geo redundancy

#### SKU Specific configurations Implemented in the pattern

* `Provisioned` Database is supported for `General Purpose`, `Hyperscale`, `Business Critical`, `Premium`, `Standard` and `Basic` SKUs.
* `Serverless` Database is supported only for `General Purpose` and `Hyperscale` SKUs.
* `read_replica_count`: This is only settable for `Hyperscale` SKUs. It sets the number of read replicas for the database. If `zone redundancy` is enabled, the minimum replica count is 1.
* `read_scale`: This is only settable for `Business Critical`, `Hyperscale` and `Premium` SKUs. It enables or disables read scale for the database. It has to be enabled for `Hyperscale` SKU .
* `zone_redundant`: This is only settable for `Premium`, `Business Critical`, `General Purpose`, and `Hyperscale` SKUs. It enables or disables zone redundancy for the database.
* `license_type`: This is only settable for `Business Critical` and `General Purpose` under `Provisioned` Database SKUs. It sets the license type for the database.
* `auto_pause_delay_in_minutes`: This is only settable for `General Purpose` Serverless SKUs. It sets the delay before the database is automatically paused, with a range of 1 hour to 7 days.
* `min_capacity`: This is only settable for `General Purpose` Serverless and `Hyperscale` Serverless SKUs. It sets the minimum capacity for the database, with a default of 0.5 cores.

#### Deploy Failover Groups Azure SQL Single Database

1. Set the variable `enable_failover_group` to `true` on the primary server.
2. Create secodnary server using pattern with `enable_failover_group` set to false - Reference in `deploytests/test/main.tf` file.
3. Secondary Server should not contain any databases.
4. The CMK Key used in the primary server creation needs to be present in the secondary region keyvault. This comes from requirement that both servers in failovergroup needs to have same key material.
5. if You dont pass any database Ids to the variable it will take all the databses created in the pattern deployment. In the reference `deploytests/test/main.tf` all databases created in the primary server pattern deployment are added to the failover group.No need to create any databases in secondary server.

Note: Due to unavailablity of two regions for testing the pattern was tested in single region for failovergroups. The reference deployment uses the same key from the primary region Keyvault. Additional things to take note of during multi region failover,

* [Failover groups overview & best practices (Azure SQL Database)](https://learn.microsoft.com/en-us/azure/azure-sql/database/failover-group-sql-db?view=azuresql)
* [Geo-replication considerations when configuring automated rotation of the TDE protector](https://learn.microsoft.com/en-us/azure/azure-sql/database/transparent-data-encryption-byok-overview?view=azuresql#geo-replication-considerations-when-configuring-automated-rotation-of-the-tde-protector)
* For a server with automated key rotation enabled, before initiating geo-replication, add the encryption key being used as TDE protector on the primary server to the secondary server. **The secondary server requires access to the key in the same key vault being used with the primary server (and not another key with the same key material)**. Alternatively, before initiating geo-replication, ensure that the secondary server's managed identity (user-assigned or system-assigned) has required permissions on the primary server's key vault, and the system will attempt to add the key to the secondary server.
* [Geo-DR and customer-managed TDE](https://learn.microsoft.com/en-us/azure/azure-sql/database/transparent-data-encryption-byok-overview?view=azuresql#geo-dr-and-customer-managed-tde)

##### **Authentication **

1. Only Entra ID can be configured by setting `azuread_authentication_only`to `True`.
2. Entra ID and SQL Auth both can be enabled by setting `azuread_authentication_only` to `false`. For `SQL Auth`, pass value for `administrator_login` and `administrator_login_password`.

##### **TDE with failover groups:**

1. **Configure Key Vaults**: Link your primary and secondary servers to Azure Key Vaults that have consistent key material. This could be the same key vault or different key vaults in different regions. In both cases the network connectivity between the priamry region and the secondary region is out of scope for the pattern.**
Please refer to the Networking SAD and the below diagram for the same.
[STAR DA-020 Intra ALZ Connectivity v0.6.docx](https://lsegroup.sharepoint.com/:w:/r/teams/LMFoundationFM/Shared%20Documents/General/02%20Design%20Docs/1%20Cloud%20Networking/STAR%20DA-020%20Intra%20ALZ%20Connectivity%20v0.6.docx?d=wea35e1f11373410a9377ff6ef63f3687&csf=1&web=1&e=BPolnZ&nav=eyJoIjoiMTkwODAzMzExNCJ9)
[Image: AzureALZNetworking]
 **To Enable auto-rotation of keys to work with TDE, The pattern recomends using the same keyvault in the primary region and esure HA through Keyvault deployment.
2. **Maintain Consistent Key Material**: If you’re using different key vaults, ensure that they have consistent key material. This is crucial for the geo-secondary server to take over using the same key.
3. **Enable Auto-Rotation of TDE Protector**: When you’re setting up TDE for your server, make sure to enable the auto-rotation of the TDE protector. This ensures that the latest version of the key is always in use.
4. **Test Failover Regularly**: Regular testing of failover is important to ensure that the SQL Database maintains access permission to both key vaults.
5. **Monitor Key Vault Redundancy**: Make use of the redundancy features of Azure Key Vault to ensure the availability of keys in case of service or region failures.
