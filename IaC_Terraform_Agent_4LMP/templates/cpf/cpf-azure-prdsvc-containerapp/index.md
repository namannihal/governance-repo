# Container App module

## Overview

This terraform module creates a Container App and associated resources.

## Prerequisites
A `container app environment` needs to be deployed first.

## Guidance

#### Usage

###### AzureRM 3.x to 4.x Upgrade Notes for Container App

Product Impact -- Medium

Users in azurerm 3.x migrating to 4.x  need to perform the following changes

  - Custom domains should be managed using a dedicated `azurerm_container_app_custom_domain` resource block. The `custom_domain` block within the `ingress` configuration is deprecated.

  - Introduced new optional variable  `initial_delay` with default value as `0` to `readiness_probe` and `startup_probe` configurations to provide proper probe timing control.

  - Wiki link for [AzureRM 4.x Upgrade](https://gitlab.dx1.lseg.com/groups/app/app-51310/azure/prdsvc/terraform/-/wikis/Terraform-AzureRM-Provider-Upgrade:-Version-3.x-to-4.x/Container-app) for details on the upgrade process.

For more details, refer to the official [AzureRM 4.x Upgrade Guide](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/guides/4.0-upgrade-guide)

###### Others

- This module deploys the Container App. Container Apps basically supports two revisions such as Single mode and Multiple mode.
- In Single mode, a single revision is in operation at any given time. In Multiple mode, more than one revision can be active at a time and can be configured with load distribution via the traffic_weight block in the ingress configuration.
- In order to restrict public access and to limit the traffic to VNET, the key combination to be used is ingress with internal load balancer + custom Vnet + external to true.
- To limit traffic to container apps environment, the key combination to be used is ingress with internal load balancer + custom Vnet + external to false.
- The identity provider to manage the user identities and authentication flow for application is not currently available as part of container app resource configuration in terraform . Selection of providers such as Microsoft, Facebook, Google, Apple, GitHub, OpenID Connect and Twitter to integrate the app authentication and it's corresponding settings have to be configured at the product end.
- Please be noted with regards to custom DNS server configuration. If your VNet uses a custom DNS server instead of the default Azure-provided DNS server, configure your DNS server to forward unresolved DNS queries to 168.63.129.16. Azure recursive resolvers uses this IP address to resolve requests. When configuring your NSG or firewall, don't block the 168.63.129.16 address, otherwise, your Container Apps environment won't function correctly. Do refer the article against DNS section.
https://learn.microsoft.com/en-us/azure/container-apps/networking?tabs=workload-profiles-env%2Cazure-cli.
- Atmost one revision can be applied at the time of container app creation, to deploy multiple traffic revisions set `revision_mode` as `Multiple`, in first apply create the traffic weight with `ingress_traffic_weight`, `latest_revision` set to true and `percentage` set to 100 (see implememtation in `.test/deployTest/main.tf`). To split traffic- comment out the first `ingress_traffic_weight` and add a another `ingress_traffic_weight` block with multiple revisions as a list and update the variable `revision_suffix` to the desired value to create second revision and apply again.

#### Security Considerations

- The repo variable `PESTER_IMAGE_POST_DEPLOYMENT` is used to refer to the latest pester image during post deployment stage, in order to install the `Az.App` package in line 74 of pipeline.yml file. Please approach the DX1 maintainers to set this up before running the validation pipeline.
- The following [policy](https://portal.azure.com/#view/Microsoft_Azure_Policy/PolicyDetailBlade/definitionId/%2Fproviders%2FMicrosoft.Management%2FmanagementGroups%2Fa1a-dev%2Fproviders%2FMicrosoft.Authorization%2FpolicyDefinitions%2FCustom-ContainerAppsMeMustEnableAzureMonitor-1.0.0) on greenfield that requires a container app to enable Azure Monitor has to be exempted before running the validation pipeline as it cannot be set through terraform or AzAPI.
- The following [policy](https://portal.azure.com/#view/Microsoft_Azure_Policy/PolicyDetail.ReactView/id/%2Fproviders%2FMicrosoft.Authorization%2FpolicyDefinitions%2F783ea2a8-b8fd-46be-896a-9ae79643a0b1/scopes~/%5B%22%2Fproviders%2FMicrosoft.Management%2FmanagementGroups%2Fa1a-dev%22%5D) on greenfield that requires a container app to disable external network access and to enforce internal-only ingress. This will limit the inbound traffic of container apps with in the container apps environment. This is achieved via setting the `external_enabled` property to `false` as the default value.
- In future, if requirement arises to change the value from `false` to `true` to restrict the traffic only with in the custom `vnet`. Please reach out to LSEG Cyber Support to exempt the current policy that denies `external_enabled` property to `true`.

#### Additional Information

- The specific attribute `termination_grace_period_seconds` defined in terraform [documentation](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/container_app) for `liveness_probe` and `startup_probe` is reported as a bug by Hashi Corp. Hence it's value cannot be configured via terraform code currently.
- This attribute has been removed explicity from the `container-app` module.
