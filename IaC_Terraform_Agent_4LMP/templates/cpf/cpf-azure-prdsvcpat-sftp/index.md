# SFTP Service Pattern

[[_TOC_]]

This readme provides an overview of a service pattern for `azure-prdsvcpat-terraform-sftp`. The solution proposed below provides an easy predefined template built on top of LSEG approved Cloud Products (with identified common configurations) and the service pattern intended to help application teams with rapid deployments of infrastructure.

Here are some of the key advantages the proposed solution offers:

- **Rapid Deployment:** Service patterns are pre-defined templates that can be easily reused which accelerates the deployment process by eliminating the need to write configurations from scratch for each deployment, saving time and effort.
- **Standardization and Consistency:** Service patterns provide standardized templates and best practices for deploying specific infrastructure that promotes consistent configurations. This ensures consistency across deployments, reducing the likelihood of configuration drifts/errors and making it easier to maintain and scale infrastructure.
- **Documentation:** Service pattern comes with built-in documentation that explain the purpose and usage of various components.
- **Security and Compliance:** Service pattern built on top of approved Cloud Products incorporate security best practices and compliance requirements, ensuring that infrastructure is deployed with security in mind from the outset. This reduces the likelihood of security vulnerabilities.
- **Reuse, Sharing and customization:** Teams can share and reuse patterns across projects and organizations. Patterns can be adapted, and customized over time as infrastructure/business requirements change.
- **Version Control:** Patterns can be version-controlled, allowing teams to track changes, roll back to previous configurations if issues arise, and collaborate more effectively through version control systems.

## Pattern Description

This section contains the details of the azure service technical use case.

### Provisioned Azure services through IaC

- Azure datalake with private endpoint.
- User managed identity.
- Datalake Gen 2 Filesystem and Path.
- Storage Account Local User.
- Azure Key Vault with Private Endpoint.
- Azure Key Vault Secrets.
- Azure App Service Plan.
- Azure Function App with Private Endpoint.
- Azure Application Insights.
- Azure Event Grid System Topic.
- Azure Event Grid Event Subscription.
- Azure Role Assignment.

### Identity management

- Pattern provides the capability to deploy user managed identity for SFTP which will be used for authentication between the Azure services.

### Secret management

- Azure Key Vault (AKV) will be used to store password or ssh private key for the local sftp users.

### Other

- AzureStorage Account with queue will be used to store the event.
- Storage Queue Event will trigger function app that will execute command to rotate ssh key pair or password for local user upon expiry.
- We need to whitelist these URLs that will download Az module inside function app that will help to execute respective command.
     - psg-prod-centralus.azureedge.net
     - psg-prod-eastus.azureedge.net
- After deploying function App, we need to trigger az cli stage in pipeline to deploy our function code to the function app. Before that , the _funczip_ zip file needs to be downloaded from the SFTP repository and unzipped.
 1. Open the SFTP-Key-Rotation/function.json
 2. Update the Queue name parameter with the queue created by the pattern. An example is given below

 ```
{
    "bindings": [
      {
        "type": "queueTrigger",
        "direction": "in",
        "name": "myQueueItem",
        "queueName": "a1a-<app-id>-dev-stq-sftp-uks-001", // Change this to the queue created by the pattern
        "connection": "AzureWebJobsStorage"
      }
    ]
  }
  ```
  3. Once the function.json is updated, the entire files should be zipped again. Please make sure you select all the files/folders including SFTP-Key-Rotation (folder), host.json, profile.ps1, requirements.ps1. And on the selection, right click -> Compressed(zip)folder with name funczip. This make sures the root of the zip file contain the host.json otherwise function will not work.
  4. The new funczip zip file can be now used to be deployed to the function app.

# Pattern Usage Guidance

## Pattern Use Cases

| Use Case                                                   | Default Behaviour                                                                                                                                                                                  | Input Control - Variable                                                                                      | Comments                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
|------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Deploy Azure KeyVault or use an existing KeyVault**      | By default, the pattern deploys a new KeyVault.                                                                                                                                                    | `key_vault_config.deploy_kv_and_pe`                                                                           | The variable `key_vault_config.deploy_kv_and_pe`, if set to true, deploys the Azure KeyVault with a private endpoint. The configurations of this KeyVault can be managed under the `key_vault_config` variable. To use an existing KeyVault, use the `key_vault_config.key_vault_id` input and set `key_vault_config.deploy_kv_and_pe` to false.                                                                                                                                                                                                                                            |
| **Create SFTP Local User Password or ssh key** | By default, the pattern will create sftp local user with password.                                                                                                                                               | `ssh_password_enabled`                                                                             | The variable `ssh_password_enabled`, if set to True, local user will be created with password that will be stored in key vault secret. The variable `ssh_password_enabled`, if set to False, local user will be created with key pair where private key will be stored in key vault secret.                                                                                                                                                                                                                       
### Prerequisites

- A Resource Group where you want to create SFTP,Function App, KeyVault, KeyVault Private EndPoint and associated resources.
- A Virtual Network and Subnet where you plan to deploy the Private Endpoint.
- An Azure Private DNS Zone to resolve the Private Endpoint using DNS name.
- Nework Connectivity : If you have multiple Virtual Networks, you might need to setup the connectivity between the Virtual Network containing Gitlab Pipeline runner and the Virtual Network where you plan to deploy the Private Endpoints for SFTP.

### Additional Information

1. This pattern creates, one datalake store with SFTP enabled. Multiple users can be created for SFTP, with either ssh key or password enabled.
2. The pattern creates a separate Storage account apart from the Data Lake Store, which is being used for the SFTP password/ key rotation purpose.
3. The resources - Event Grid System Topic, Event Grid Event Subscription, App Service Plan, Log Analytics Workspace & Application Insight are being deployed once and will be used 4. for password/ key for all SFTP users.
5. The pattern gives flexibility to include exisiting keyvault to be part of the SFTP secret rotating infrastructure. If not user can configure to use separate new keyvault which pattern will be able to deploy.
6. The pattern creates key vault secret to store the ssh private key and ssh password, the name for these secrets gets created with a suffix    -sftp-privatekey & -sftp-password respectively. It is suggested to not create any secret in the same key vault with these suffix as the event for secret expiration will be triggered based on these names, this will be true when adding an existing keyvault, since the event is scoped to the KeyVault resource.
7. The policy for  DNS creation for function app, is not configured properly, hence once the function app is created, raise an SRE ticket to get the DNS corrected. This step should be completed before the function deployment.
8. The function app for secret rotation would need to be deployed separately using the pipeline and az cli once the terraform deployment is completed. This would require the scm
endpoint to become resolvable to the private IP. The function app zip file is in the root folder of the module with name `funczip.zip` and this can be deployed using the
`az functionapp deployment source config-zip -g "<application-resource-group>" -n "<function-app-name>" --src "funczip.zip"`. Sample pipeline used for testing can be found in
`.gitlab-pipelines\pipeline.yml` file in `az-cli-test` stage.
9. This pattern does not support the deployment of Flex consumption plan for function app for now as the function deployment process is different for this type of function app.
10. Secrets are configured to expire for 365 days. The SecretNearExpiry event will be fired <=30 days for expiry. Hence the secrets will be rotated every 11 months, and the clients would need to redownload the new secrets from the Key Vault.
