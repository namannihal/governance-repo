# Linux Web App Module


## Overview

This terraform module creates a Linux Web App and its associated resources. The module supports robust configuration, deployment slots for blue-green deployments, slot swapping with traffic distribution, and comprehensive security controls. It is designed for enterprise use with support for managed identities, authentication, client certificates, connection strings, and conditional deployment of deployment slots.

## Prerequisites

- An existing `Resource Group`.
- A `Virtual Network`, `Subnet` for VNET integration of linux webapp.
- A `Service Plan` to host linux webapp and a `Key Vault`.

## Guidance

#### Usage

###### Deployment Slots Configuration

- Create multiple deployment slots using the `deployment_slots` variable
- Configure separate `site_config`, `auth_settings`, and `connection_string` for each slot
- Swap traffic between slots using `azurerm_web_app_active_slot`
- Distribute traffic across multiple slots using `slot_traffic_routing`
- Apply network policies per slot using `vnet_route_all_enabled`

## Others

- Deployment slots enable blue-green deployments and staged rollouts of the Linux Web App. Each slot is a separate instance with its own configuration:
- Terraform will perform a name availability check as part of the creation progress, if this Web App is part of an App Service Environment terraform will require `Read permission` on the ASE for this to complete reliably.
- This module is creating the Linux Web App with publishing model as `Container`. If required to use `Code` as a Publish mode then the related parameters needs to be added in the `application_stack` block under `site_config` [Application_Stack](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/linux_web_app#application_stack).
- `auto_heal_enabled` and `auto_heal_setting` both (together) also be included in future module versions as per the requirement under `site_config`.
- `always_on` must be explicitly set to false when using Free, F1, D1, or Shared Service Plans.
- `docker_registry_url`, `docker_registry_username`, and `docker_registry_password` replace the use of the app_settings values of DOCKER_REGISTRY_SERVER_URL, DOCKER_REGISTRY_SERVER_USERNAME and DOCKER_REGISTRY_SERVER_PASSWORD respectively, these values will be managed by the provider and should not be specified in the `app_settings` map.
- One and only one of ip_address, service_tag or virtual_network_subnet_id must be specified.
- App Service plan and Linux Web App must be in the same region.
- The `client_id` value is always considered an allowed audience.
- `default_provider` setting is only needed if multiple providers are configured, and the `unauthenticated_client_action` is set to `RedirectToLoginPage`.
- One of `client_secret_setting_name` or `client_secret_certificate_thumbprint` must be specified.
- Application Insights code-less monitoring for Linux containers currently supports .NET, Java and Node.js applications. If your container uses a different language, consider including the Application Insights SDK in your container.
- `JBOSSEAP` requires a `Premium` Service Plan SKU to be a valid option.
- The valid version combinations for `java_version`, `java_server` and `java_server_version` can be checked from the command line via `az webapp list-runtimes --linux`.
- `key_vault_reference_identity_id` requires User Assigned Identity type, post enabling role assignment. The User Assigned Identity ID used for accessing KeyVault secrets. The identity must be assigned to the application in the identity block.
- Deployment slots support `site_config`, `auth_settings`, `auth_settings_v2`, `storage_account`, `connection_string`, `logs`, `backup`, and `identity` blocks.
- Deployment slots do NOT support `sticky_settings` blocks.
- Slot traffic routing allows gradual traffic migration between slots using `rampUpRules`.
- Active slot can be set via `azurerm_web_app_active_slot` resource; use `overwrite_network_config = true` to swap network settings as well.
**IMPORTANT NOTE**

There are certain `active_directory_v2` variables that might be needed by some applications in the future, and are `READ-ONLY` in the azurerm provider, such as `allowed_applications` and `jwt_allowed_client_applications`. Even when using `azapi_update_resource`, these variables are updated on the first run, but if the same code is redeployed, the `AzAPI` does not reapply the changes. This results in the default settings from AzureRM `overriding` the updates.

To work around this, you can use the `null_resource` resource block. For example:

```
resource "null_resource" "update_web_app_authv2" {
  triggers = {
    always_run = timestamp()
  }
  provisioner "local-exec" {
    command = <<-EOF
      az webapp auth update \
          --resource-group ${var.resource_group_name} \
          --name ${module.azure-prdsvc-terraform-linuxwebapp.name} \
          --set identityProviders.azureActiveDirectory.validation.defaultAuthorizationPolicy.allowedApplications=["${var.auth_allowed_applications}"]
    EOF
    interpreter = ["bash", "-c"]
  }  
}

```

#### Security Considerations

- Assigning the `virtual_network_subnet_id` property requires [RBAC permissions](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration#permissions) on the subnet. `virtual_network_subnet_id` also requires to have a delegation to Microsoft.Web/serverFarms.
- `Azure doesn't allow to create a Private endpoint on a delegated subnet`, hence, if there is a need to access or add Keyvault secrets then please use a non-delegated subnet to create a Private Endpoint.
