# CPF Module JSON Schemas

This directory contains JSON schema files generated from the LSEG Cloud Product Framework (CPF) documentation.
Each file describes a CPF Terraform module and provides the structured metadata an AI agent needs to generate
valid Terraform code for migrating applications to Azure.

## Directory Contents

| File | Purpose |
|------|---------|
| `_catalog.json` | Master index of all 252 CPF modules with summary stats |
| `cpf-azure-prdsvc-*.json` | Single-service modules (e.g., Key Vault, Virtual Network, AKS) |
| `cpf-azure-prdsvcpat-*.json` | Service patterns (multi-service bundles, e.g., PostgreSQL + Private Endpoint) |
| `cpf-azure-prdapppat-*.json` | Application patterns (full app-ready stacks, e.g., AKS + PostgreSQL + Redis) |

## Schema Structure

Each schema file follows this structure:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "cpf_id": "cpf-azure-prdsvc-<service>",
  "module_type": "service | service-pattern | application-pattern",
  "azure_service": "<Human-readable service name>",
  "module_name": "<Full module title>",
  "gitlab_repository": "<Documentation URL>",
  "terraform_source": "<git:: URL to Terraform module>",
  "terraform_requirements": {
    "terraform": ">= 1.5.0",
    "azurerm": ">= 3.51"
  },
  "prerequisites": ["Resource Group", "Virtual Network", ...],
  "azure_resources_created": [
    { "terraform_resource": "azurerm_key_vault.this", "type": "resource" }
  ],
  "terraform_usage": {
    "module_call_template": {
      "module_label": "<short name>",
      "source": "<git:: URL>",
      "version": "latest"
    }
  },
  "inputs": {
    "type": "object",
    "required": ["app_id", "environment", ...],
    "properties": {
      "app_id": {
        "type": "string",
        "description": "...",
        "required": true
      }
    }
  },
  "outputs": {
    "id":   { "description": "The resource ID." },
    "name": { "description": "The resource name." }
  },
  "agent_instructions": {
    "summary": "...",
    "module_type_notes": "...",
    "naming_convention": "Resource names are auto-generated by the module using app_id, environment, and region.",
    "prerequisite_modules": [...]
  }
}
```

## Module Types

| Type | CPF Prefix | Description | When to use |
|------|-----------|-------------|-------------|
| **service** | `prdsvc` | Provisions a single Azure resource type | Building blocks — combine multiple for a full solution |
| **service-pattern** | `prdsvcpat` | Bundles a primary service + supporting config (Private Endpoint, DNS, RBAC) | When you need an opinionated, secure, ready-to-use service |
| **application-pattern** | `prdapppat` | Full infrastructure stack for a specific app archetype | When migrating a specific app type (e.g., AKS+DB+Cache) |

## Agent Usage Instructions

### Step 1 — Identify required modules

Consult the `_catalog.json` to find modules matching the application's needs:
```
modules[].azure_service  → filter by Azure service type
modules[].module_type    → prefer service-pattern or application-pattern when available
modules[].output_count   → modules with outputs can be referenced by other modules
```

### Step 2 — Load the module schema

Read the JSON schema file for each required module. Key fields:

- **`terraform_source`** — use as the `source` argument in the Terraform `module` block
- **`inputs.required[]`** — these parameters **must** be provided; the module will fail without them  
- **`inputs.properties`** — full list of configurable variables with types and defaults
- **`outputs`** — reference these values from other modules using `module.<label>.<output_name>`
- **`prerequisites`** — provision these resources first (usually Resource Group, VNet, Key Vault)
- **`azure_resources_created`** — list of Terraform resources the module manages

### Step 3 — Generate Terraform code

Use the `terraform_usage.module_call_template` as a starting template:

```hcl
module "<module_label>" {
  source = "<terraform_source>"

  # Required inputs (no default — must be provided)
  app_id              = var.app_id
  environment         = var.environment
  resource_group_name = module.resourcegroup.name

  # Optional inputs (override defaults as needed)
  # account_replication_type = "ZRS"
}
```

### Step 4 — Wire module dependencies

Use `module.<label>.<output_name>` to pass outputs from prerequisite modules:

```hcl
module "keyvault" {
  source              = "<keyvault terraform_source>"
  resource_group_name = module.resourcegroup.name
  # ...
}

module "storageaccount" {
  source              = "<storageaccount terraform_source>"
  resource_group_name = module.resourcegroup.name
  key_vault_id        = module.keyvault.id        # ← output reference
  # ...
}
```

## Common Patterns for Application Migration

### Web Application (Linux/Windows)
1. `cpf-azure-prdsvc-resourcegroup`
2. `cpf-azure-prdsvc-virtualnetwork` + `cpf-azure-prdsvc-subnet`
3. `cpf-azure-prdsvcpat-keyvaultprivateendpoint`
4. `cpf-azure-prdsvc-appserviceplan`
5. `cpf-azure-prdsvcpat-linuxwebapp` or `cpf-azure-prdsvcpat-windowswebapp`

### Containerized Application (AKS)
- Use `cpf-azure-prdapppat-akspostgresqlredis` for apps needing AKS + PostgreSQL + Redis (full pattern)
- OR compose individually: `kubernetescluster` + `postgresqlserver` + `rediscache` + `containerregistry`

### Microservices with Messaging
- `cpf-azure-prdapppat-servicebus` — Service Bus application pattern
- `cpf-azure-prdapppat-eventgrid` — Event Grid application pattern

### Database-centric Applications
- `cpf-azure-prdsvcpat-mssql` — SQL Server with Private Endpoint
- `cpf-azure-prdsvcpat-postgresql` — PostgreSQL Flexible Server with Private Endpoint
- `cpf-azure-prdsvcpat-cosmosdb` — CosmosDB with Private Endpoint

## Important Notes

1. **Module versioning** — The `version` field in the template is set to `"latest"`. In production, pin to a specific git tag using `?ref=vX.Y.Z`.

2. **Naming convention** — CPF modules auto-generate resource names from `app_id`, `environment`, `location`, and optionally `instance`/`context`. Do NOT pass custom names unless the module explicitly supports it.

3. **RBAC** — The Service Principal running Terraform requires `Contributor` + `User Access Administrator` permissions on the target subscription/resource group.

4. **Private Endpoints** — By default all CPF modules disable public network access. Private Endpoints are managed separately via `cpf-azure-prdsvc-privateendpoint` or are built into the service patterns.

5. **Inputs coverage** — Not all modules have fully documented inputs in this schema set; inputs coverage reflects what is published in the CPF documentation portal. Refer to the GitLab repository for the complete variable definitions.
